# Актуальный Codex harness · 2026-10-10

Это снимок используемых правил, пяти навыков, трёх ролей и экспериментальных обработчиков. Он позволяет выбрать нужные части и сверить архитектуру. Эффективность всей системы ещё не установлена; наличие исходников не означает, что каждый обработчик наблюдался в работе.

[Общая схема архитектуры](../ARCHITECTURE.md) показывает связи между правилами, навыками, помощниками и восстановлением работы.

## Как устроена работа

1. Главный агент определяет задачу. Простое объяснение или точечная правка выполняются напрямую.
2. Для существенной работы он читает один процесс: code-workflow либо research-workflow. Для продуктовой задачи добавляет только нужную область product-work; для редактуры — clear-writing и нужный язык. Decision-review нужен при существенном выборе. Артефактные навыки среды остаются обязательными по своему назначению.
3. Главный агент ведёт диалог и собирает результат. Luna получает независимую ограниченную работу; Astra — архитектуру или существенную неопределённость. Отдельный sol-reviewer сохранён для явно выбранного критического ревью. Наличие роли не делает делегирование обязательным.
4. На существенной границе сохраняются результат, факты и следующий шаг. Человек подключается при блокирующем выборе или недостающем разрешении; пауза на каждом этапе не требуется.
5. Агент сопоставляет результат с запросом. Проверки и тесты выполняются в пределах пользовательского разрешения. Трассы читаются для конкретного сбоя или оценки эффективности.

Пример: при исследовании конкурентов достаточно research-workflow и market. Редактор, три агента, Jev и hook не нужны, если нет отдельной причины их использовать.

## Что выбирать и как переносить

Начните с аудита без изменений: [каталог компонентов и условия выбора](../workspace-inspector/references/component-selection.md). Установка inspector **не устанавливает** этот каталог навыков, роли или обработчики.

- `AGENTS.md`: объединить нужные разделы с действующими правилами, сохранив приоритеты проекта. `<CODEX_HOME>` — обозначение пути, а не готовая команда. Абсолютный checkpoint-вызов намеренно исключён; его создаёт установка выбранного Unsnooze на целевой машине.
- `skills/`: копировать только выбранные каталоги в каталог навыков целевого Codex. Штатный openai-docs и навыки документов/таблиц/изображений предоставляются средой; сюда не скопированы.
- `agents/`: определения из текущей установки. Имена моделей сохранены как факт настройки, а не обещание доступности в каждом аккаунте или версии. До применения проверить поддержку модели, роли и способ её регистрации в целевом клиенте; не заменять основную модель автоматически.
- `runtime/bounded-read.mjs`: выборочное чтение большого HTML/лога средствами Node.js; не выполняет скрипты страницы и не заменяет визуальную проверку.
- Остальные `runtime/`: экспериментальная связка выбора пакета и ограничения контекста. Нужны Node.js, совместимый host adapter для UserPromptSubmit / PreToolUse / PostToolUse и корректные session/turn/tool payload. Ветка исходников не регистрирует эти hooks автоматически. `context-guard.mjs` уже импортирует `runtime.mjs`; policy JSON должен лежать рядом. Не подключать обработчик вслепую к другому клиенту.

Для возврата сохранить исходные файлы до слияния, восстановить только изменённые файлы и убрать только добавленную регистрацию hooks. Чужие настройки целиком не заменять.

## Наблюдённые настройки

В исходной установке: основная модель `gpt-6.1-sol`, reasoning `medium`, краткое резюме рассуждений, порог compaction 80 000 токенов, ограничение вывода инструмента 4 000 токенов. Это настройки среды, а не доказанный оптимум. `runtime/context-policy.json` содержит текущие экспериментальные лимиты; они не равны квотам подписки. Полный пользовательский config, доверенные пути, ключи, переписка, состояния hooks и резервные копии исключены.

## Границы работы

- Code-workflow и research-workflow согласованы с общей политикой: Astra для архитектуры и существенной неопределённости, sol-reviewer для отдельно выбранного ревью. Доступность модели и фактический вызов зависят от среды.
- Context policy задаёт Sol для обычного worker, а глобальные правила предлагают Luna для ограниченной работы. Роль Luna и общий default worker — разные пути; фактический выбор следует устанавливать по вызову и возвращённой модели.
- При установке нового runtime живые сессии его обработчика не наблюдались. Успех записи файлов не доказывает загрузку пакета, соблюдение инструкций или запуск Astra.
- Runtime хранит последние 1 000 событий на сессию. Его отчёт не считает стоимость checkpoint и billed tokens и не объединяет rollout с Jev. Счётчики — диагностические признаки, а не оценка качества.
- Загрузка выбранного пакета ограничивает новые поступления текста, но не удаляет уже прочитанный контекст. Gate рассчитан на сотрудничающего агента, может обходиться разрешёнными bootstrap-командами и не является защитной границей.
- Сохранённый checkpoint не доказывает успешное восстановление. Unsnooze/Jev — отдельный [компонент](../unsnooze/README.md); Jev по умолчанию выключен.

## Что проверено в этой публикации

Исходники экспортированы из установленной конфигурации; исключены личные пути и эксплуатационные данные. Сопоставлены приоритеты общих правил, условия чтения новых справок, маршрутизация помощников и разрешения на тесты. Проверены синтаксис шести изменённых JavaScript-файлов Unsnooze, локальные ссылки документации и совпадение пяти SKILL.md с установленными версиями. Метаданные навыков проверены ограниченной структурной проверкой: штатный валидатор не запустился из-за отсутствия PyYAML. Установка на чистую машину, сквозное восстановление Unsnooze и живая проверка hooks в рамках публикации не проводились. Автоматический установщик из личной среды не включён: он зависит от уже зарегистрированного локального guard.

Расход и полезность следует оценивать на обычных задачах: тип задачи → фактические вызовы → результат → исправления → доступные счётчики. Без сопоставимых задач это наблюдения, а не доказательство экономии. Пользователю не требуется запускать отдельные тестовые задания.
