# ТЗ: Unsnooze for Codex — экономное продолжение долгих задач

Статус документа: рабочее ТЗ форка. Главный сценарий — Codex; совместимость с
остальными агентами не должна определять архитектуру.

## 1. Цель

Автоматически продолжать долгую задачу Codex после сброса лимита, не заставляя
пользователя следить за остатком квоты и не перечитывая без необходимости всю
историю. При этом восстановление должно быть проверяемым: система хранит
контрольные точки, автоматически собирает пакет восстановления, использует
compact по понятному бюджету и считает стоимость всех служебных операций.

Главный критерий успеха — не минимальная цена одного compact, а минимальная
полная стоимость завершённой задачи при приемлемом качестве продолжения.

## 2. Термины и роли

- **Checkpoint** — короткое долговечное состояние задачи: цель, подтверждённые
  факты, сделанные изменения, открытые вопросы, следующий шаг и проверки. Это
  страховка и содержимое будущего recovery bundle; он не заменяет историю
  текущей сессии.
- **Recovery bundle** — автоматически собранная техническая упаковка checkpoint
  для новой сессии: идентификаторы, окружение, состояние файлов, причина
  остановки и результат проверки свежести. Модель не пишет второй пересказ.
- **Compact** — сжатие контекста внутри текущей сессии Codex, чтобы продолжить
  работу с меньшим активным контекстом. Это не отдельный документ и не
  гарантированное долговечное хранилище.
- **Resume** — продолжение существующей сессии после сброса лимита, когда это
  возможно и экономически оправданно.
- **Fresh recovery** — запуск новой сессии из recovery bundle. Это проверяемая
  оптимизация второго этапа, а не основной безопасный путь: при любой
  неопределённости используется `codex resume`.
- **Jev gate** — необязательная проверка checkpoint отдельной моделью.
  Модель не управляет процессом целиком, а возвращает короткое структурированное
  решение по фиксированным критериям.

## 3. Основной пользовательский сценарий

1. Пользователь запускает задачу Codex как обычно.
2. Пока задача работает и кэш контекста тёплый, система создаёт checkpoint
   только в значимых точках, а не после каждого шага.
3. Для новых сессий fork настраивает штатный auto-compact Codex по безопасному
   порогу. Он не печатает `/compact` и не прерывает активный ход. Регулярные
   checkpoint обеспечивают недавнее долговечное состояние задачи.
4. Если задача остановилась из-за лимита, система фиксирует recovery episode,
   автоматически собирает recovery bundle и ждёт без участия пользователя.
5. После сброса в v1 предпринимается безопасный resume существующей сессии.
   Параллельно `hybrid-shadow` считает, соответствовал ли recovery bundle
   требованиям
   fresh recovery, но новую сессию не создаёт.
6. В v1.1 fresh recovery разрешается только для checkpoint с
   `content_valid=true` и `freshness=current`. При `missing`,
   `content_invalid` или `stale` всегда используется `codex resume`.
7. Пользователь получает уведомление только если требуется его решение или
   восстановление окончательно не удалось.

Legacy-настройки `usageWarn` и `contextGuard` по умолчанию выключены. Порог
80/95% не создаёт пользовательскую обязанность: checkpoint и compact работают
системно.

Предупреждение «осталось 10%» не требует от пользователя нажимать Stop. Это
внутренний сигнал оркестратору: на ближайшей границе хода обновить checkpoint.
Сам compact остаётся штатным автоматическим механизмом Codex; активный ход не
прерывается и пользователь ничего не нажимает.

## 4. Когда создавать checkpoint

Checkpoint создаётся после материального изменения состояния:

- подтверждена или отвергнута важная гипотеза;
- принято архитектурное решение;
- завершён самостоятельный кусок работы;
- перед передачей ответственности и после принятия результата;
- перед compact, остановкой по лимиту или fresh recovery;
- перед рискованной операцией и после её проверки;
- при явном запросе пользователя.

Checkpoint не создаётся после обычного чтения файла, каждого вызова инструмента
или каждого промежуточного сообщения. Для долгого активного хода допускается
таймер-страховка, но только если с прошлого checkpoint изменилось материальное
состояние. Начальное значение: 15 минут; затем настраивается по статистике.

Содержательная часть, которую формирует модель:

```json
{
  "goal": "string",
  "confirmed": ["string"],
  "changes_artifacts": ["string"],
  "open_issues": ["string"],
  "next_responsibility": "string",
  "verification": ["string"],
  "schema_version": 1
}
```

Daemon добавляет отдельный технический envelope, не поручая модели угадывать
системное состояние:

```json
{
  "root_task_id": "string",
  "session_id": "string",
  "created_at": "ISO-8601",
  "source_turn_id": "string",
  "cwd": "string",
  "worktree": "string|null",
  "model": "string|null",
  "reasoning_effort": "string|null",
  "sandbox": "string|null",
  "permissions_fingerprint": "string|null",
  "git_head": "string|null",
  "workspace_fingerprint": "string|null",
  "context_tokens": "number|null",
  "schema_version": 1
}
```

Требования: атомарная запись, версия схемы, путь вне git по умолчанию, отсутствие
секретов и полного транскрипта, ссылка на конкретный commit/diff или артефакт
вместо копирования больших данных.

## 5. Recovery bundle и восстановление

Recovery bundle формируется машиной из последнего checkpoint и проверяемого
состояния рабочей директории. Он не содержит второго модельного пересказа, а
ссылается на checkpoint и добавляет:

- идентификатор корневой задачи и текущей сессии;
- причину перехода: limit, compact, crash или manual;
- текущий commit, dirty-state и список релевантных файлов;
- точную следующую команду/операцию;
- критерий, по которому новая сессия поймёт, что восстановилась правильно.

Порядок восстановления:

1. Проверить, что исходная задача остановилась именно из-за лимита, а не была
   завершена, отменена пользователем или аварийно завершена.
2. После сброса попытаться возобновить существующую Codex-сессию.
3. Проверить успех по первому осмысленному progress event, а не по факту запуска
   процесса.
4. В v1 не создавать свежую сессию автоматически; только записать решение
   shadow-классификатора и фактический результат `codex resume`.
5. В v1.1 fresh recovery допускается только при `content_valid + current` и
   single-flight lease.
6. Не отправлять произвольный пользовательский «resume prompt»: системный
   recovery bundle является единственным источником контекста новой сессии.
7. Не запускать одновременно две ветки одной задачи.

Checkpoint сам по себе недостаточен для безрискового fresh recovery: лимит может
наступить после последнего сохранения. Любое последующее изменение файлов или
существенная команда помечают checkpoint потенциально stale, пока новая точка
не зафиксирует результат. Готовность к fresh recovery состоит из двух независимых
признаков:

- `content_valid`: checkpoint понятен, непротиворечив и содержит следующий шаг;
- `freshness=current`: после него не было незаписанной значимой работы и
  workspace snapshot совпадает.

Jev может оценивать только `content_valid`. `freshness` определяет daemon по
turn/tool-событиям и снимку рабочей директории; модель не должна его угадывать.

## 6. Политика compact

Compact выполняется штатным механизмом внутри активной сессии Codex. Fork не
эмулирует `/compact`: он добавляет ownership-marked настройки в
`~/.codex/config.toml`, а Codex сам выполняет сжатие. Порог считается по
`body_after_prefix`, то есть по части контекста после перенесённого префикса
предыдущего compact.

Начальная конфигурация:

```toml
model_auto_compact_token_limit = 160000
model_auto_compact_token_limit_scope = "body_after_prefix"
```

Порог 160k используется для стандартного каталожного окна 272k (около 258k
эффективного окна). Для другого известного окна installer вычисляет 62% его
эффективной ёмкости. Если каталог модели недоступен, абсолютный порог не
угадывается: сохраняется нативный адаптивный порог Codex, а fork задаёт только
`body_after_prefix`. Уже заданные пользователем значения не перезаписываются.

Событие `ContextCompaction` только записывается в телеметрию. Оно не делает
checkpoint устаревшим, поскольку не меняет состояние задачи или workspace, и
fork не запускает второй compact. Пауза менее 30 минут может называться только
`warm-cache candidate`; фактический cache hit известен из usage ответа после
запроса. Ручное действие пользователя не требуется.

## 7. Jev как дополнительный слой

### 7.1 Checkpoint Gate

Jev получает только кандидат checkpoint и четыре атомарных вопроса: ясна ли
цель, исполним ли следующий шаг, нет ли внутренних противоречий и достаточно ли
состояния для продолжения. Он возвращает вероятности, а контроллер собирает из
них строго структурированный результат:

```json
{
  "verdict": "pass | review | fail",
  "minimum_probability": 0.0,
  "probabilities": {
    "goal_clear": 0.0,
    "next_step_executable": 0.0,
    "internally_consistent": 0.0,
    "sufficient_for_continuation": 0.0
  }
}
```

Критерии:

- цель понятна без транскрипта;
- подтверждённое отделено от предположений;
- следующий шаг исполним;
- изменения и проверки можно найти;
- нет внутренних противоречий;
- объём не превышает лимит.

Jev не генерирует и не исправляет текст. В `shadow` его решение только пишется
в метрики. В `enforce` только уверенный `fail` может поставить
`content_valid=false`; `review`, timeout или ошибка сохраняют deterministic
path и не блокируют основную задачу. API-вызов выполняется отдельным worker с
compare-and-set по `checkpoint_id`, поэтому поздний ответ не портит новую
ревизию.

### 7.2 Compaction Guard

Вторая, отдельная роль Jev — оценить, не потеряет ли предполагаемый compact
критически важную незавершённую информацию. Она включается только после того,
как Checkpoint Gate покажет пользу. Один и тот же длинный prompt нельзя
использовать для проверки качества checkpoint и для принятия решения о compact.

## 8. A/B-тест Jev

A/B — встроенная настройка, а не ручной режим. При включении новые корневые
задачи автоматически распределяются между группами:

- **control** — весь основной конвейер работает без вызова Jev;
- **treatment** — Jev вызывается в выбранной области.

Единица рандомизации — вся lineage задачи. Назначение вычисляется один раз:

```text
bucket = hash(experiment_id + "\0" + root_task_id) mod 100
treatment, если bucket < allocation_percent; иначе control
```

Группа сохраняется в состоянии задачи, наследуется всеми resume/fresh recovery
и не меняется после перезапуска, обновления конфигурации или смены session id.
Это исключает contamination, когда одна задача частично проходит с Jev, а
частично без него.

Настройки:

```toml
[experiments.jev]
enabled = false
allocation_percent = 50
id = "jev-v1"
scope = "checkpoint_gate" # checkpoint_gate | compaction_guard | all
mode = "shadow"           # shadow | enforce
```

- `shadow`: treatment вызывает Jev и пишет его решение, но не меняет поведение;
- `enforce`: валидное решение Jev может изменить checkpoint или отложить
  compact в пределах описанных правил;
- изменение `id` начинает новую версию эксперимента только для новых задач;
- существующие задачи сохраняют старое назначение.

Эксперимент запускается с `allocation_percent=50`, `scope=checkpoint_gate`,
`mode=enforce`. Jev оценивает каждый сохранённый checkpoint treatment-задачи,
даже если задача не достигала лимита и не требует unsnooze. Контрольная группа
не вызывает Jev. Enforce применяется только к новым lineage после смены
experiment id; существующие задачи сохраняют прежние arm и mode. Compaction
Guard остаётся отдельным экспериментом.

На Windows ключ Jev задаётся интерактивно:

```powershell
unsnooze experiment jev key set
```

По умолчанию эксперимент выключен, и ключ не нужен для обычного Unsnooze. После установки этой ветки пользователь сам вводит ключ в своём терминале; агенту и в файлах проекта его передавать не следует. Проверьте `unsnooze experiment jev key status`, затем отдельно включите `unsnooze experiment jev shadow` или `unsnooze experiment jev on`. Без ключа включённый treatment даёт ошибку оценки и fail-open; отсутствие блокировки не означает, что Jev проверил checkpoint. На macOS/Linux локальное защищённое хранение ключа не реализовано: используйте `TYPESAFE_API_KEY` через собственный менеджер секретов.

Ввод скрыт. Ключ не записывается в историю PowerShell, конфигурацию, state или
логи: на диске остаётся только зашифрованный Windows DPAPI CurrentUser blob.
Проверить наличие или удалить его можно командами `key status` и `key remove`.
Переменная окружения `TYPESAFE_API_KEY` остаётся явным override и способом
запуска на платформах, для которых безопасное локальное хранилище ещё не
реализовано. Сам эксперимент включается отдельно: хранение ключа не должно
неожиданно менять поведение.

Основной анализ — intent-to-treat: сравниваются все назначенные задачи, даже
если Jev не был вызван из-за ошибки. Дополнительно строится exposed-анализ по
задачам, где модель реально ответила.

## 9. Телеметрия и стоимость

Для каждого служебного события записываются:

- `root_task_id`, `session_id`, experiment id и arm;
- тип события: checkpoint, recovery_bundle, compact, resume, fresh_recovery,
  jev_call;
- входные/выходные токены, cached input, длительность и оценочная стоимость;
- причина события и результат;
- версия схемы checkpoint/recovery bundle;
- число повторов, ошибок и пользовательских вмешательств.

Итоговые метрики по control/treatment:

- доля задач, продолженных без вмешательства;
- доля успешных fresh recovery;
- потерянные/противоречивые checkpoint и recovery bundle;
- число исправлений checkpoint и доля принятых исправлений;
- лишние compact и compact, предотвращённые guard;
- токены и деньги на служебные операции;
- общая стоимость завершённой задачи;
- время до завершения и число повторных действий;
- субъективная оценка пользователя, если она была явно дана.

Отчёт разделяет `observed` и `estimated`. Нельзя утверждать «сэкономлено X» для
отдельной задачи, если альтернативный способ реально не выполнялся. Честное
сравнение строится между A/B-когортами по фактическим token/cache показателям;
контрфактическая экономия помечается оценкой.

Телеметрия локальная и по умолчанию не отправляется наружу. Должны быть команды
экспорта JSON/CSV и сброса статистики с явным подтверждением. Хранение полного
prompt/response Jev не требуется: достаточно хэша входа, структурированного
решения, счётчиков токенов и кода ошибки.

## 10. Что убрать из upstream Unsnooze

Для Codex-ветки не нужны как пользовательские функции:

- произвольный custom resume prompt;
- `contextGuard` upstream;
- предупреждения о 80/95% расхода, требующие реакции пользователя;
- Claude-specific menu automation и Claude-specific autocompact flags;
- очередь новых пользовательских prompt как часть восстановления.

Их следует удалять поэтапно после покрытия текущего поведения тестами. Простое
скрытие из UI недостаточно: они не должны влиять на state machine. Уведомления
оставляются только для ошибок, запроса решения или окончательного завершения.

## 11. Состояния

```text
ACTIVE
  -> CHECKPOINTING -> ACTIVE
  -> COMPACTING -> ACTIVE
  -> LIMIT_STOPPED -> ARMED -> PENDING

PENDING
  -> RECOVERING_EXISTING -> RECOVERED -> ACTIVE
  -> SHADOW_FRESH_DECISION -> RECOVERING_EXISTING
  -> FRESH_RECOVERY (v1.1, content_valid + current only) -> RECOVERED -> ACTIVE
  -> CANCELLED | FAILED | NEEDS_USER

ACTIVE -> COMPLETED | CANCELLED | FAILED
```

Каждый переход идемпотентен. На одну lineage и один limit episode действует один
lease и не более одного recovery. Повторный daemon после падения/перезапуска
Windows продолжает незавершённый переход, а не запускает второй. Нужны clock
skew tolerance, jitter, ограничение повторов, exponential backoff и защита от
цикла fresh-session → новый limit → fresh-session. Ожидающее восстановление
можно отменить.

## 12. Этапы реализации

1. **Foundation:** схема конфигурации, стабильное A/B-назначение по lineage,
   сохранение назначения и CLI статуса. Это реализуется первым.
2. **Durable context:** writer/reader checkpoint, recovery bundle builder,
   `current/stale`, атомарность,
   валидация схемы и тест восстановления без транскрипта.
3. **Codex lifecycle:** feature detection версии Codex/JSONL, различение
   complete/cancelled/crashed/limit, resume existing, single-flight lease,
   подтверждение прогресса и `hybrid-shadow` для fresh recovery.
4. **Compaction integration:** ownership-marked native Codex config,
   адаптивный порог по каталогу модели и распознавание `ContextCompaction`.
5. **Jev adapter:** shadow Checkpoint Gate, строгая схема ответа, timeout,
   fallback и лимит стоимости; затем enforce.
6. **Telemetry/report:** события, стоимость, A/B-отчёт, JSON/CSV export.
7. **Fresh recovery v1.1:** включить только для `content_valid + current`,
   сохранив resume fallback
   и все параметры окружения: worktree, cwd, model, reasoning, sandbox и
   permissions.
8. **Simplification:** удалить Claude-specific и пользовательски бесполезные
   upstream-функции после переноса нужных сценариев.

Интеграция в Codex config/AGENTS использует ownership markers. Uninstall удаляет
только принадлежащие форку блоки и возвращает исходную конфигурацию. Checkpoint и
метрики имеют локальные ACL, retention и явный purge.

## 13. Приёмочные критерии

- Задача после лимита продолжается без пользовательского Stop/Resume.
- Resume не создаёт параллельный дубль задачи.
- В v1 fresh recovery работает только в shadow и не создаёт новую сессию.
- В v1.1 fresh session никогда не создаётся при missing checkpoint,
  `content_valid=false` или `freshness=stale`.
- Файловая мутация, не отражённая в checkpoint, принудительно выбирает resume.
- Завершённые и отменённые задачи не возобновляются.
- Один limit episode создаёт не более одного recovery даже после рестарта.
